# Essl F22 SDK Design

**Date:** 2026-10-24

**Status:** Approved for planning; implementation not started.

## Goal

Provide a synchronous, dependency-free Python SDK for administering the
eSSL/ZKTeco F22-family terminal at `192.168.1.27:4370`, including user
management, attendance retrieval, fingerprint template inspection, and
non-destructive access blocking/unblocking.

## Validated Device Behavior

These facts were verified against the hardware on 2026-10-24. They are
requirements, not assumptions.

- The terminal is reachable over TCP at port `4370`.
- The device reports:
  - `~Platform=ZLM60_TFT`
  - `~DeviceName=x 2008`
  - `~SerialNumber=JJA1242200334`
  - firmware `Ver 6.60 Apr 13 2022`
- A communication key of `0` authenticates successfully.
- At validation time the device held:
  - 295 user records
  - 266 fingerprint templates
  - 11,895 attendance records
- User records are 72 bytes on this device.
- Attendance records are 40 bytes on this device.
- The byte at user-record offset `2` is the permission token.
  - `E0` (`privilege & 0x01`) is documented as the enable bit.
  - `E0=0` means enabled; `E0=1` means disabled.
  - **This firmware stores `E0` but does not enforce it for access.**
  - A user with `E0=1` can still verify a fingerprint and unlock the door.
  - `CMD_REFRESHDATA`, `CMD_DISABLEDEVICE`/`CMD_ENABLEDEVICE`, and a
    database refresh did not make `E0` effective.
- Access is enforced by the **timezone** assigned to the user or inherited
  from the user's group.
- Assigning a user to a timezone whose every day has a start time greater
  than its end time produces `invalid time period` on the terminal and
  prevents the door relay from unlocking.
- A denied access attempt is **not** written to the attendance log.
- Restoring the user's original timezone assignment restores verification
  and door unlock.
- User `uid=295` / PIN `13` was used for validation:
  - original permission token `0`
  - group `1`
  - `timezone_flag=0` (inherit group timezone)
  - one valid fingerprint template `fid=9`, flag `1`, entry size `958`
  - group `1` uses timezone `1`
  - timezone `1` allows `00:00-23:59` every day
- Deny-all timezone `6` was written as:
  - `slot=6`
  - every day `23:59 -> 00:00`
  - encoded on the wire as
    `struct.pack("<I", slot) + bytes([23, 59, 0, 0]) * 7`
- The block was applied with `CMD_USERTZ_WRQ` (`24`) and
  `CMD_REFRESHDATA` (`1013`); no user record or fingerprint template was
  deleted.
- The user was unblocked by restoring `timezone_flag=0`; verification and
  unlock returned.
- The device normalizes `timezone_flag=0` by zeroing the personal timezone
  fields. An unblocked user therefore reads back as
  `flag=0, tz1=0, tz2=0, tz3=0`.

## Scope

In scope:

- Synchronous TCP client.
- Python 3.12 and newer.
- Standard library only at runtime.
- Device information, free-space counters, and device time.
- Read all users, read one user, create/update a user, delete a user.
- Read fingerprint templates and inspect their metadata.
- Read attendance records.
- Read and write access timezones, groups, and per-user timezone
  assignments.
- Non-destructive block/unblock of a user through access timezones.
- Local persistence of each user's original timezone assignment.
- Unit tests with a fake transport and optional read-only hardware tests.

Out of scope for this version:

- UDP, serial, or USB transports.
- ADMS/Push protocol.
- Fingerprint enrollment, upload, or deletion.
- Face, card, or photo management.
- Real-time event streaming.
- A command-line interface.
- Cross-device synchronization of block state.
- Restoring a deny-all timezone slot after the last user is unblocked. The
  SDK reserves one unused slot for blocking for the lifetime of the device
  configuration.

## Block/Unblock Algorithm

Blocking must never edit or delete the user record or fingerprint templates.

`block_user(uid)`:

1. Read the user and its current `UserTimeZone`.
2. Ensure the device has a reserved deny-all timezone slot:
   - If local state already records one, read it from the device and reuse
     it when it is still deny-all.
   - Otherwise read all users, groups, and timezones.
   - Collect every timezone slot referenced by a group or by a user that
     uses a personal timezone.
   - Choose the highest-numbered slot that is not referenced and whose
     definition is the default all-day `00:00-23:59` schedule.
   - Write the deny-all definition to that slot with `CMD_TZ_WRQ` and call
     `CMD_REFRESHDATA`.
   - Save the slot in local state.
   - Raise `NoFreeTimeZoneSlotError` if no eligible slot exists.
3. If the user's current assignment already points at the block slot, return
   `BlockResult(already_blocked=True, ...)` without writing.
4. Save the original `UserTimeZone` in local state, keyed by device serial
   number and `uid`.
5. Write `UserTimeZone(uid, use_personal=True, tz1=block_slot, tz2=0, tz3=0)`
   with `CMD_USERTZ_WRQ`.
6. Call `CMD_REFRESHDATA`.
7. Read the assignment back and verify it matches. If verification fails,
   attempt to restore the original assignment and raise
   `DeviceVerificationError`.
8. Return `BlockResult`.

`unblock_user(uid)`:

1. Read the user.
2. Look up the saved original timezone.
3. If no saved state exists, restore the group timezone
   `UserTimeZone(uid, use_personal=False)` and set `state_found=False`.
4. Write the original assignment, refresh, and verify.
5. Delete the saved state.
6. Return `UnblockResult`.

`is_user_blocked(uid)` reads the user's assignment and compares it with the
reserved block slot. `get_blocked_users()` reads the local state.

The block operation leaves `User.privilege` unchanged. The `E0` bit is not
used because this firmware does not enforce it.

## State Persistence

`SqliteBlockStateStore` stores:

- `original_user_timezone(device_serial, uid, use_personal, tz1, tz2, tz3)`
- `block_timezone(device_serial, slot)`

The default database path is platform-appropriate:

- macOS: `~/Library/Application Support/essl_f22/state.db`
- Windows: `%LOCALAPPDATA%/essl_f22/state.db`
- other: `$XDG_DATA_HOME/essl_f22/state.db` or
  `~/.local/share/essl_f22/state.db`

If state is lost, unblocking falls back to the group timezone. The block
timezone slot remains reserved.

## Protocol Layer

- TCP framing:
  - magic `0x5050`, `0x7D82`
  - little-endian 32-bit payload length
  - payload header `<4H`: command, checksum, session id, reply id
- Checksum is calculated over the 8-byte header with the checksum field
  zero, plus the command data, using the ZKTeco one's-complement algorithm.
- The checksum is calculated before incrementing the reply id; the packet
  carries the incremented reply id.
- Connection starts with `CMD_CONNECT=1000` and reply id `65534`; the
  increment wraps to `0` for the first packet.
- If the connect reply is `CMD_ACK_UNAUTH=2005`, send
  `CMD_AUTH=1102` with `make_commkey(comm_key, session_id, ticks=50)`.
- Large reads use:
  - `CMD_DATA_WRRQ=1503` with `<bhii` `(1, command, fct, ext)`
  - the response is `CMD_DATA=1501` for inline data, or `CMD_ACK_OK=2000`
    with the total size at `data[1:5]`
  - chunks are read with `CMD_DATA_RDY=1504` and `<ii` `(start, size)`
  - a chunk response may be `CMD_PREPARE_DATA=1500` followed by
    `CMD_DATA=1501` and `CMD_ACK_OK=2000`
  - release the buffer with `CMD_FREE_DATA=1502`
- The maximum chunk size is `0xFFC0` bytes.

## Error Handling

All public errors derive from `ESSL22Error`:

- `DeviceConnectionError`
- `DeviceAuthenticationError`
- `DeviceTimeoutError`
- `ProtocolError`
- `CommandError` (includes the reply code)
- `DeviceVerificationError`
- `UserNotFoundError`
- `NoFreeTimeZoneSlotError`
- `StateStoreError`

No parser may raise `IndexError`, `struct.error`, or `KeyError` for truncated
or malformed device data; those cases become `ProtocolError` with a useful
message.

## Testing

- Unit tests use a scripted `FakeTransport`; no hardware is required.
- Parser tests use the captured records and blobs from the validated device.
- Block-manager tests use an in-memory state store and a fake device.
- Hardware tests are marked `hardware` and skipped unless `ESSL_F22_HOST`
  is set. They are read-only by default.
- Manual block/unblock validation remains documented because it requires a
  person at the door.

## Firmware Caveat

This SDK's block mechanism is a valid access-control timezone assignment,
not a write to the documented `E0` bit. It is reliable on the validated
firmware. Other ZKTeco firmware may enforce `E0`; using timezones still
blocks access there, but the SDK's behavior should be re-validated on each
new device family.
